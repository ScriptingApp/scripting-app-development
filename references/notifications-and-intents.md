# Notifications and Intents

Read this for `notification.tsx`, local rich notifications, `intent.tsx`, Shortcuts, or Share Sheet work.

## Rich notifications

- Locate current Notification APIs from official `llms.txt` documentation first.
- Scheduling must explicitly enable the documented custom UI option (currently described as `customUI: true`); merely adding `notification.tsx` is not enough.
- Render expanded UI from `notification.tsx` with the documented presentation API.
- Read event-specific metadata from the current notification context rather than assuming main-script memory is available.
- Map notification actions to explicit, meaningful URL scheme or documented action routes. Validate input when the script is re-opened.
- Test real delivery, expansion, action tap, and cold-start/re-trigger behavior on device.

## Shortcuts and Share Sheet intents

- Put the handler in `intent.tsx` and declare only the supported input types in the project/Intent configuration.
- Inspect `Intent.shortcutParameter` and/or typed input collections only after verifying their API. Check type and presence before use.
- Return a documented result such as `Intent.text(...)`, `Intent.url(...)`, `Intent.json(...)`, or `Intent.file(...)` through `Script.exit(result)`.
- Every path—success, empty input, unsupported type, cancellation, and failure—must return or cleanly terminate.
- Present a page only when user interaction is genuinely needed; when it closes, return a result rather than leaving the extension running.
- Large files may exceed extension memory constraints. Prefer the documented in-app execution route when required.

## Shared constraints

Notification actions and Intents are external input boundaries. Validate URLs, files, text size, and parameters. Do not trust a route merely because it was generated by the script. Final verification requires a real notification, Shortcuts action, or Share Sheet invocation.
